# v1.7.5 新码直推规格

业主决定（2026-09-17）：
- **新码直接推，旧码推飞书。** 按每条记录的编号分流，一条记录只走一条路，不双写。
- 直推接口先和拉载一样开放（不设口令）。
- 新二维码是成品码（镭射在铝壳上），和磁芯无关。1.7.5 不带 dba76c0 的「磁芯自动流水码」。

现场行为不变的底线：旧码（飞书标签链接 / 260YN#### 这类序号 / 只有磁芯编号 / 没有编号）的记录，推飞书的逻辑、字段、重试、CSV 与 1.7.4 完全一致。

---

## 1. 新码格式（与 SOAI「明码编号规范」逐位一致）

9 位 = 年 2 位数字 + 代次 2 个字母 + 流水 4 位数字 + Damm 校验 1 位数字，例如 `26HK04426`。

- 代次字母只能是 `ACFHKLRTWY`，按这个顺序映射为 0–9 参与校验。
- Damm 表（与 `D:/code/SOAI/frontend/soai-frontend/src/lib/serialCode.ts`、`D:/code/SOAI/backend/ww_order_api.py` 相同）：

```
[0,3,1,7,5,9,8,6,4,2]
[7,0,9,2,1,5,4,8,6,3]
[4,2,0,6,8,7,1,3,5,9]
[1,7,5,0,9,8,3,4,2,6]
[6,1,2,3,0,4,5,9,7,8]
[3,6,7,4,2,0,9,5,8,1]
[5,8,6,9,7,2,0,1,3,4]
[8,9,4,5,3,6,2,0,1,7]
[9,4,3,8,6,1,7,2,0,5]
[2,5,8,1,4,3,6,7,9,0]
```

- 校验位 = 对前 8 位依次 `i = DAMM[i][d]`（第 3、4 位的 d 是字母在 `ACFHKLRTWY` 中的下标），最终 i。
- 二维码内容：`https://www.soaipower.com/t/<9位码>`。

### 识别函数 `parse_finished_code(text) -> str | None`（Python 与 TS 各一份，行为相同）

1. `None`/非字符串 → `None`；先去首尾空白（与前端 `String.prototype.trim()` 同一组字符，两边实测一致）。
2. 若匹配 `^https?://(www\.)?soaipower\.com/t/([0-9A-Za-z]{9})/?$`，取第 2 组；否则若整段是 9 位字母数字，取整段；都不是 → `None`。
   **整条不区分大小写**（业主 2026-09-17 确认）：扫码枪开着大写锁定时扫出来的是 `HTTPS://WWW.SOAIPOWER.COM/T/26hk04426`，必须也能认出来；码本身还要过 Damm 校验，放宽不会误认。
3. 候选转大写，必须匹配 `^[0-9]{2}[ACFHKLRTWY]{2}[0-9]{5}$`，且校验位正确，才返回大写码；否则 `None`。
4. 旧码 `260YN0062`、`2602N0186`、飞书 27 位 token、飞书 `/record/` 链接都必须返回 `None`。

**「新码记录」的定义：** 归一化之后 `parse_finished_code(record_number)` 不为 `None`。

## 2. autotest 后端（`D:/code/autotest/backend`）

### 2.1 `run_test` 编号归一化（在写 CSV 之前）
- 若 `parse_finished_code(req.record_number)` 有值 → `record.record_number = 该码`。
- 否则若 `parse_finished_code(req.serial_code)` 有值（前端旧流程把扫到的整段文字当序列码传上来）→ `record.record_number = 该码`，`record.serial_code = ''`。
- 其余情况原样不动（与 1.7.4 相同）。

### 2.2 分流（原 `uploader.push_async(...)` 调用处）
- 新码记录 → `cloud_uploader.enqueue(record_dict)`，**不调飞书**。
- 其余 → 原来的 `uploader.push_async(...)`，代码路径不改。
- 飞书凭证缺失时旧码记录照旧静默不推；新码直推不依赖飞书凭证。

### 2.3 直推载荷里的单条记录（client 生成）
| 字段 | 取值 |
|---|---|
| `upload_id` | `uuid.uuid4().hex`（32 位小写十六进制），入队时生成一次，重试不变 |
| `product_code` | `record.product_code` |
| `test_time_ms` | 与飞书 `_build_fields` 完全相同的算法：`datetime.strptime(timestamp, '%Y-%m-%d %H:%M:%S').timestamp()*1000` 取整（本机时区）；解析失败用当前时间并记 WARN |
| `company` / `line` / `station` / `deployment_id` | `state.get_deployment()` |
| `serial_code` / `record_number` / `core_number` | 归一化后的值，空串转 `null` |
| `overall` | `PASS` / `FAIL` |
| `items` | `{label: number}`，label 与值规则和飞书 `_build_fields` 完全一致（`_item_label`；取 `value_display`，不是有限数就退回 `value`，仍不是就跳过；NA 项照样包含）。必须抽成一个共用函数，飞书输出不得变化 |
| `calibration_id` | 与飞书「扣偏校验ID」同源，可为 `null` |

### 2.4 本地队列 `backend/cloud_uploader.py`
- 文件（进程 cwd 下，与 `feishu_pending.jsonl` 同目录）：`cloud_pending.jsonl`（待传）、`cloud_rejected.jsonl`（服务端明确退回的，带原因，不再重试）。
- `enqueue(record)`：加锁 → 追加一行 JSON（`allow_nan=False`）→ `flush` + `os.fsync` → 返回 `upload_id`，然后唤醒线程。**先落盘再发送**；`run_test` 返回前记录已在磁盘上。
- 后台线程（daemon，FastAPI startup 启动，不依赖飞书凭证）：启动 5 秒后开始；每轮读待传，每批最多 50 条 POST；有剩余立刻下一批；失败等 60 秒；可被 `enqueue` / 手动重试唤醒。
- 发 HTTP 时不持锁；收到结果后加锁重写 `cloud_pending.jsonl`（临时文件 + fsync + `os.replace`），只删掉本批 `accepted` 与 `rejected` 里的 id；期间新入队的行必须保留。
- 队列里损坏的行：移入 `cloud_rejected.jsonl`（原因「本地队列行损坏」），不阻塞其他行。
- 地址：常量 `https://www.soaipower.com/api/erp/production/ingest`，可被 `config.json` 的 `cloud_ingest_url` 覆盖（测试用）。
- 超时 `(5, 30)`。
- 状态：`status()` → `{url, pending, rejected, last_ok_at, last_error, running}`。
- 新接口：`GET /api/cloud-upload/status`，`POST /api/cloud-upload/retry`（只唤醒线程，返回 `{ok:true, triggered:true, pending}`）。
- 日志用 `logs.log`，中文。

### 2.5 其他
- 撤掉 dba76c0 引入的磁芯自动流水码（`serial_code.py`、`run_test` 里的自动发码、`/api/serial-code/*`、`state.py` 与 `feishu_uploader.py` 里对应新增部分），只改工作区，不动 git 索引、不提交。
- `APP_VERSION = '1.7.5'`，`CHANGELOG.md` 加 1.7.5 条目。
- 测试放 `D:/code/autotest/tests/`（pytest，用系统 `python` 运行）。`conftest.py` 必须：切到临时目录（仓库根有真实 `feishu_config.json`，在根目录起后端会写线上飞书）、全局拦截真实网络（requests / httpx / socket 连接一律报错），任何用例都不能访问 soaipower.com 或飞书。

## 3. SOAI 后端接收端（`D:/code/SOAI/backend`）

### 3.1 接口
- `GET /api/erp/production/ingest/ping` → `{"ok":true,"service":"test-ingest","auth_required":false}`
- `POST /api/erp/production/ingest`，不鉴权（与 loadtest 一致）。

请求：
```json
{"source":"autotest","app_version":"1.7.5","records":[ R, ... ]}
```
- 信封错误（不是 JSON 对象、`records` 不是列表、为空、超过 200 条）→ HTTP 400 `{"ok":false,"error":"..."}`。

逐条校验，不合格的放进 `rejected`，合格的写库：
- `upload_id` 匹配 `^[0-9a-f]{32}$`
- `product_code` 非空字符串，≤ 200 字符
- `test_time_ms` 是整数（不是 bool），在 2020-01-01 到「现在 + 1 天」之间
- `overall` ∈ `PASS` / `FAIL`
- `items` 是对象，≤ 300 个键；键是非空字符串 ≤ 100 字符；值是 int/float（不是 bool）且有限
- `serial_code` / `record_number` / `core_number` 至少一个非空；各自 `null` 或字符串 ≤ 200
- `company` / `line` / `station` / `deployment_id` / `calibration_id`：`null` 或字符串 ≤ 200
- 同一请求里 `upload_id` 重复：后面的判为 rejected

### 3.2 写入 `test_records`（合格记录一次 upsert，`on_conflict='feishu_record_id'`）
| 列 | 值 |
|---|---|
| `feishu_record_id` | `'up_' + upload_id`（幂等键；飞书同步产生的 id 都以 `rec` 开头，不会冲突） |
| `feishu_table_id` | `''`（让「补序号回写飞书」的 `if ftid and frid` 为假） |
| `timestamp` | `test_time_ms` 转 UTC ISO 8601，精确到秒 |
| `product_code` / `overall` / `items` | 原样（items 为 jsonb 对象） |
| `serial_code` / `record_number` / `core_number` | 空串转 `null` |
| `company` / `line` / `station` / `deployment_id` | 去首尾空格，空串转 `null` |

不写 `identifier` / `is_valid` / `is_core_inspection`（生成列）、`id`、`inserted_at`。`calibration_id` 和 `app_version` 暂不入库（表里没有列）。

### 3.3 响应
- 成功：HTTP 200 `{"ok":true,"accepted":[upload_id...],"rejected":[{"upload_id":...,"error":"..."}]}`
- 写库异常：HTTP 500 `{"ok":false,"error":"..."}`（客户端整批保留重试）

### 3.4 兼容
- 核对 `production_sync.py` 的补序号、标签回填、分类统计，以及其他读 `test_records` 的接口，遇到 `feishu_table_id=''`、`feishu_record_id='up_…'` 的行不报错、不去改飞书；需要时只做最小的跳过判断。
- 测试放 `backend/tests/`，用假 Supabase 客户端（参照 `test_rd_progress_api.py`），不连真实数据库。
